# Rpi5Display 0.1.15 — Hardware-Verified Pre-release

> **Known issue:** after longer use, the tested Raspberry Pi 5 can still develop severe desktop lag/hang even while otherwise idle. This invalidates the earlier "stable" designation. Use v0.1.15 for testing only until the long-run degradation is understood and fixed.

Rpi5Display 0.1.15 contains the Raspberry Pi 5 KMDOD VSync, framebuffer-performance, signing and idle-power work that was merged to `main`, but it is **not currently considered stable** because the long-run lag/hang remains reproducible.

## What is verified

Hardware verification was performed on a Raspberry Pi 5 Model B running Windows 11 ARM64 with the validated exp0.7 UEFI display handoff and a 1920x1080 @ 60 Hz HDMI display path.

Verified on that configuration:

- driver starts successfully with StartDevice Stage 8 / STATUS_SUCCESS;
- Device Manager reports ProblemCode 0;
- firmware timing and EDID handoff are accepted;
- PixelValve VSync is enabled through Windows' DISPLAYONLY_VSYNC control path;
- real hardware VSync interrupts reach dxgkrnl at the expected ~60 Hz cadence;
- Windows exposes 1920x1080 @ 60 Hz;
- framebuffer updates use write-combined memory copies rather than register-buffer writes;
- immediate mouse/menu responsiveness is materially better than the early 0.1.13 path;
- test-signing and package validation pass.

## Known unresolved issue

After extended runtime, the same tested system can again become **laggy or effectively hung**, including after idle periods with no application workload.

The earlier short 0.1.15 captures were healthy but did not cover a sufficiently long reproduction window. A later real-world test reproduced the degradation, so the release is being reclassified as **pre-release / known issue**.

The next required diagnostic is a support bundle captured **while the system is actively degraded and before reboot**. 0.1.15 includes high-resolution QPC Present timing, pixel-work counters, VSync state, power-transition evidence, CPU/load and display-idle policy specifically for this investigation.

## Key fixes since 0.1.8

- consumes validated UEFI/ACPI display timing and EDID handoff;
- adds KMDOD VSync control and scanline support;
- maps the assigned BCM2712 PixelValve resource for the active HDMI path;
- accepts Windows 11 KMDOD `DXGK_INTERRUPT_DISPLAYONLY_VSYNC` control requests;
- reports hardware VSync through `DXGK_INTERRUPT_DISPLAYONLY_VSYNC`;
- fixes the first-edge interrupt-enable ordering race;
- provides a provisional timing phase until the first real hardware VSync anchor;
- preserves post-mortem VSync and interrupt diagnostics;
- removes the StartDevice VSync timeout dependency;
- replaces slow per-scanline register-buffer framebuffer writes with write-combined memory copies;
- rate-limits diagnostic registry churn during routine VSync control;
- adds high-resolution QPC Present timing and pixel-work diagnostics;
- accepts valid display adapter/monitor D-state notifications without failing `DxgkDdiSetPowerState`;
- removes synchronous full-screen blank/flush work from the power callback;
- repairs the framebuffer on the next normal Present after returning to D0;
- hardens the disposable lab signing certificate against reasonable target/CI clock skew.

## Important limitations

This is a **test-signed display-only driver**, not a complete Raspberry Pi graphics stack.

- known unresolved long-run lag/hang;
- not WHQL/production signed;
- no VideoCore VII / V3D render acceleration;
- no hardware video-decode driver yet;
- no hardware cursor implementation yet;
- broader monitor/mode coverage is not hardware-verified;
- native BCM2712 display power gating is not implemented;
- sleep/hibernate coverage remains limited.
